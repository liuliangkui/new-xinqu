## 一、编写目标

本文档规范面向「人工智能编程 agent」（如 DeepSeek、Claude、Cursor 等）设计，核心目标只有一个：

**让 AI 在只阅读设计文档的情况下，输出的代码在功能、交互、视觉、数据模型上与设计稿保持高度一致。**

为达到该目标，所有应用模块文档必须同时满足：

1. **无歧义**：同一句话只能有一种理解方式。
2. **可量化**：所有尺寸、颜色、间距、状态、权限都有明确数值或枚举值。
3. **可映射**：每一处 UI 都能对应到具体组件名、字段名、接口名。
4. **可验证**：每个功能都有至少一条可自动化验证的断言。
5. **双端一致**：PC 端与移动端必须分别描述，不能混为一谈。

## 二、文档统一结构

每份应用模块文档必须按以下章节顺序编写，缺失任一章节视为不合格。

| 章节 | 是否必填 | 说明 |
|---|---|---|
| 1. 文档基础信息 | 必填 | 版本、日期、对应原型、对应规范、适用角色 |
| 2. 机器指令块 | 必填 | 供 AI 先读取的全局约束 |
| 3. 模块定位与目标 | 必填 | 一句话定位、业务痛点、量化价值 |
| 4. 使用角色与权限 | 必填 | 角色清单、数据可见性、功能权限矩阵 |
| 5. 核心业务流程 | 必填 | 状态机、正常流、异常流、流程图 |
| 6. 页面清单与路由 | 必填 | 所有页面、URL/路由、页面类型 |
| 7. 页面结构与布局 | 必填 | 每页布局、组件、响应式规则 |
| 8. 核心字段规范 | 必填 | 字段编码、类型、约束、权限、渲染方式 |
| 9. 交互设计要点 | 必填 | 搜索、筛选、操作反馈、空态、异常处理 |
| 10. 接口契约（前端视角） | 必填 | 接口名、出入参、场景说明 |
| 11. 验收断言清单 | 必填 | 可自动化验证的测试断言 |
| 12. 关联与扩展 | 必填 | 关联模块、易遗漏点、待确认问题 |

## 三、机器指令块（每份文档顶部）

每份文档基础信息下方必须包含一段机器指令块，格式如下：

```markdown
## 机器指令块

开发本模块前，AI 必须先读取并遵守以下全局约束：

- **技术栈**：Vue 3 + TypeScript + Pinia + Vue Router + Ant Design Vue 4.x + Tailwind CSS
- **组件库**：必须使用《鑫渠组件库清单与命名规范.md》中注册的组件名，禁止自行发明组件名
- **图标**：全部使用 SVG 图标或 Iconfont，禁止引用 PNG/JPG 图标
- **样式变量**：颜色、字号、间距必须使用《鑫渠全局设计系统规范.md》中的 CSS 变量
- **响应式断点**：
  - PC 宽屏：>=1440px
  - PC 标准：1024px-1439px
  - 平板：768px-1023px
  - 移动端：<768px
- **权限模型**：基于 RBAC + 数据范围，角色编码见《华鑫角色职责与用户故事.md》
- **数据规范**：字段命名必须与本文档「核心字段规范」完全一致
- **接口规范**：接口路径、字段命名必须与本文档「接口契约」完全一致
- **验收标准**：开发完成后必须对照本文档「验收断言清单」逐项验证
```

## 四、字段规范编写标准

字段描述禁止使用「客户名称」「项目金额」这类只有中文名的写法。每个字段必须包含以下 8 项：

| 属性 | 说明 | 示例 |
|---|---|---|
| 字段编码 | 英文/拼音驼峰或下划线编码 | `customerName`、`projectAmount` |
| 中文名称 | 页面显示名称 | 客户名称 |
| 数据类型 | String / Number / Date / Boolean / Enum / Array / Object | String |
| 是否必填 | 是 / 否 / 条件必填 | 是 |
| 长度/格式约束 | 最大长度、正则、精度 | 最长 100 字符 |
| 默认值 | 无默认值则写「无」 | 无 |
| 数据来源 | 手工录入 / 系统生成 / 字典 / 计算 | 手工录入 |
| 读写权限 | 谁可见、谁可编辑、是否脱敏 | 全员可见，负责人可编辑 |

### 4.1 枚举字段必须给出完整枚举值

错误示例：

```markdown
| 业务类型 | 标签 | 招标 / 非招标 / TP / 捐赠 |
```

正确示例：

```markdown
| 字段编码 | 中文名称 | 枚举值 | 说明 |
|---|---|---|---|
| businessType | 业务类型 | 1: 招标 | 公开/院内招标 |
|  |  | 2: 非招标 | 常规销售 |
|  |  | 3: TP | 第三方合作/托管 |
|  |  | 4: 捐赠 | 设备捐赠 |
```

### 4.2 状态字段必须给出状态机

每个状态字段必须给出：状态编码、状态名称、可执行操作、下一状态集合、触发条件。

示例：

```markdown
| 状态编码 | 状态名称 | 可执行操作 | 下一状态 | 触发条件 |
|---|---|---|---|---|
| 0 | 草稿 | 编辑、删除、提交 | 1 | 点击「提交」按钮 |
| 1 | 审批中 | 审批通过、驳回、撤回 | 2/4 | 上级领导点击通过/驳回 |
| 2 | 生效中 | 录入跟进、结束 | 5 | 完成所有审批节点 |
| 4 | 被驳回 | 编辑、重新提交 | 1 | 报单人修改后重新提交 |
| 5 | 已结束 | 查看、导出 | - | 流程闭环 |
```

## 五、组件规范编写标准

每处 UI 描述必须映射到具体组件。组件描述格式：

```markdown
**组件**：XqSearchBar
**位置**：列表页第三层筛选区左侧
**Props**：
- `v-model`: String，绑定搜索关键词
- `placeholder`: String，默认「搜索客户/项目/联系人」
- `allowClear`: Boolean，默认 true
- `pinyinSearch`: Boolean，默认 true，支持拼音首字母搜索
**事件**：
- `@search(keyword)`: 回车或点击搜索图标触发
- `@reset`: 清空搜索词触发
**PC 端宽度**：240px
**移动端宽度**：100%，吸顶显示
```

### 5.1 禁止模糊组件描述

错误示例：

```markdown
页面顶部放一个搜索框，可以搜索客户和项目。
```

正确示例：

```markdown
使用 XqSearchBar 组件，placeholder 为「搜索客户/项目」，pinyinSearch=true，宽度 PC 端 240px，移动端 100% 吸顶。
```

## 六、流程规范编写标准

每个核心业务流程必须包含：

1. **流程名称与目标**
2. **参与角色**
3. **流程图（ASCII 或 Mermaid）**
4. **步骤表（编号、角色、操作、系统校验、输出）**
5. **异常分支表（异常场景、触发条件、处理方式、页面反馈）**
6. **状态流转表**
7. **权限校验点（每个步骤校验什么角色、什么数据范围）**

### 6.1 步骤表示例

```markdown
| 步骤 | 角色 | 操作 | 系统校验 | 输出 |
|---|---|---|---|---|
| 1 | 报单人 | 点击「新建意向」 | 校验今日新建上限 | 打开新建弹窗 |
| 2 | 报单人 | 填写客户、项目、类型、金额 | 校验必填项、格式、客户是否存在 | 表单高亮错误 |
| 3 | 系统 | 提交时自动查重 | 校验是否存在冲突意向 | 无冲突进入步骤 4，有冲突进入步骤 5 |
| 4 | 上级领导 | 初审通过/驳回 | 校验审批权限 | 状态变为「生效中」或「被驳回」 |
| 5 | 厂家经理/负责人 | 冲突裁决 | 校验双人审批权限 | 状态变为「生效中」或「冲突无效」 |
```

## 七、响应式双端编写标准

每个页面必须分别描述 PC 端和移动端的布局。禁止只写 PC 端或只写一句话「移动端适配」。

### 7.1 必须说明的内容

| 项目 | PC 端 | 移动端 |
|---|---|---|
| 布局结构 | 几栏、占比、抽屉/弹窗 | 单列、底部固定按钮、折叠面板 |
| 导航 | 侧边栏/顶部 Tab | 底部 Tab / 顶部返回 |
| 表格处理 | 完整列展示 | 卡片列表或横向滚动 |
| 筛选处理 | 平铺或高级筛选抽屉 | 底部弹出筛选面板 |
| 手势操作 | 悬停、点击 | 滑动、下拉刷新、长按 |
| 字段显示 | 全部显示 | 按优先级折叠，核心字段优先 |

### 7.2 示例

```markdown
#### PC 端布局

- 列表页：左侧 280px 筛选面板，右侧表格/卡片，顶部统计卡片横向排列
- 详情页：右侧抽屉宽度 720px，分三段：头部信息、页签导航、内容区

#### 移动端布局

- 列表页：单列卡片列表，顶部搜索吸顶，筛选入口在搜索右侧，点击弹出底部筛选面板
- 详情页：全屏页面，顶部固定返回按钮 + 标题，底部固定「保存/提交」按钮
- 手势：左滑卡片显示快捷操作（跟进/分配），下拉刷新列表
```

## 八、接口契约编写标准

每个模块必须给出前端视角的接口契约，格式：

```markdown
### 8.1 获取意向列表

- **接口名**：getIntentionList
- **请求方式**：POST
- **路径**：/api/v1/intention/list
- **入参**：

| 字段编码 | 类型 | 必填 | 说明 |
|---|---|---|---|
| pageNum | Number | 是 | 页码，默认 1 |
| pageSize | Number | 是 | 每页条数 |
| keyword | String | 否 | 搜索关键词 |
| status | Number | 否 | 状态筛选 |
| businessType | Number | 否 | 业务类型筛选 |

- **出参**：

| 字段编码 | 类型 | 说明 |
|---|---|---|
| list | Array<Object> | 意向列表 |
| total | Number | 总条数 |
| pageNum | Number | 当前页码 |
| pageSize | Number | 每页大小 |
```

## 九、验收断言编写标准

每个核心功能必须至少写 3 条可自动化验证的断言。断言格式：

```markdown
#### 断言 1：新建意向必填校验

**前置条件**：用户已登录，角色为报单人，已进入意向列表页
**操作**：点击「新建意向」，不填写任何字段直接点击「提交」
**预期结果**：
- 客户名称、项目名称为红色高亮
- 提示文案「请填写必填项」
- 提交接口未被调用

#### 断言 2：意向搜索支持拼音首字母

**前置条件**：列表中存在「张三」负责的意向
**操作**：在搜索框输入「zs」
**预期结果**：列表筛选出负责人包含「张三」的意向
```

## 十、版本控制规范

1. 每份文档必须有独立的版本号，与应用模块版本、原型版本、规范版本同步。
2. 每次更新必须在「版本记录」表中新增一行，说明更新内容。
3. 版本号规则：
   - v1.0：初始发布
   - v1.1：局部补充
   - v1.5：结构性调整
   - v2.0：重大重构
4. 文档中引用的其他文档版本必须明确标注，避免 AI 读取错误版本。

## 十一、常见错误清单

编写完成后，必须检查以下错误是否出现：

| 错误类型 | 示例 | 修正方式 |
|---|---|---|
| 模糊描述 | 「页面顶部放一个搜索框」 | 写明组件名、props、尺寸、位置 |
| 缺少字段编码 | 「客户名称」 | 补充 `customerName` |
| 缺少枚举值 | 「状态有审批中、已通过」 | 补充状态编码和触发条件 |
| 缺少移动端描述 | 「移动端适配即可」 | 单独写一节移动端布局 |
| 缺少验收断言 | 无断言章节 | 为每个核心功能补充断言 |
| 真实 emoji | 使用 ✓ / ✗ / ⚙ | 改为「通过/不通过」或 ASCII 符号 |
| 缺少权限说明 | 「管理员可以操作」 | 写明具体角色编码和数据范围 |
| 缺少接口契约 | 只描述页面 | 补充接口名、出入参 |
