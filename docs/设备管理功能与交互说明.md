## 一、模块概述

### 1.1 模块定位

设备管理是鑫渠 CRM 业务管理域的核心模块，面向 IVD 行业「设备即阵地」的业务特点，覆盖设备从采购交付、装机验收、运行维保、调拨退机到报废处置的全生命周期。设备是试剂复购、售后服务、客户粘性的物理载体，设备管理模块的核心目标是把分散在合同、工单、仓库、客户现场的设备资产统一数字化，让每台设备的状态、位置、保修、利用率、关联试剂都清晰可见。

### 1.2 解决的核心问题

| 问题 | 说明 |
|---|---|
| 设备资产散落 | 设备信息分散在合同、ERP、售后系统、Excel 中，没有统一台账 |
| 保修空窗流失收入 | 保修到期未被及时发现，续保窗口被竞品抢占 |
| 设备状态不明 | 不知道某台设备当前是正常、维修中、闲置还是报废 |
| 设备与试剂割裂 | 不清楚某台设备实际消耗哪些试剂、消耗量如何 |
| 投放设备失控 | TP/捐赠设备装机后缺少持续跟踪，ROI 无法评估 |
| 售后派单缺少上下文 | 工程师上门前看不到设备历史维修、保修、配件信息 |

### 1.3 带来的业务价值

- **资产可视化**：建立全公司统一的设备主数据与台账。
- **收入可预测**：基于设备保有量、保修到期、试剂消耗推导续保和复购机会。
- **服务可闭环**：设备档案与售后工单、拜访记录、时间线双向关联。
- **投放可追踪**：TP/捐赠设备从装机到试剂消耗的 ROI 可量化。
- **阵地可防守**：设备地图帮助销售看清每家医院的「我方/竞品」设备布局。

## 三、典型业务场景

### 3.1 销售代表完成新装机建档

- **谁**：负责该医院的销售代表。
- **在什么情况下**：医院完成设备到货、装机验收后，需要将设备纳入系统管理。
- **做什么**：在设备管理列表页点击「+ 新建设备」，选择客户与科室，填写品牌、型号、序列号、装机日期、保修截止日期、投放模式等信息并提交。
- **达成什么**：系统生成以序列号为唯一标识的设备档案，状态为「已装机」；客户 360° 设备地图同步更新，关联意向状态同步为「已成交/已装机」，并生成设备时间线首条记录。

### 3.2 商务运营跟进保修续保

- **谁**：商务运营人员与设备负责人（销售代表/销售经理）。
- **在什么情况下**：系统每日扫描发现某设备保修截止日期在 90/60/30/7 天内到期。
- **做什么**：系统向负责人、销售经理、商务运营推送预警消息；负责人在设备详情页点击「续保」，创建续保意向或售后服务单。
- **达成什么**：续保完成后更新保修截止日期与保修类型，设备状态保持「运行中」，避免保修空窗被竞品抢占，续保金额计入绩效。

### 3.3 设备管理员审批报废

- **谁**：销售代表/售后工程师发起，销售经理初审，设备管理员终审。
- **在什么情况下**：设备达到报废标准、合同到期退机或无法修复。
- **做什么**：发起人在设备详情页发起退机/报废申请，填写原因并上传退机签收单/报废证明；销售经理初审通过后，设备管理员终审。
- **达成什么**：审批通过后设备状态变为「已报废」，进入报废台账，不再计入活跃设备统计与保修预警，保留完整历史档案以备审计。

### 3.4 售后工程师现场维修并回写状态

- **谁**：负责该设备的售后工程师。
- **在什么情况下**：设备出现故障，销售/售后/客户发起报修。
- **做什么**：售后工程师在设备详情页点击「报修」创建售后工单，上门维修后记录维修内容、配件、工时并关闭工单。
- **达成什么**：工单创建时设备状态自动变为「维修中」；工单关闭后状态恢复为「运行中」（可正常使用）或进入报废申请（无法修复），维修记录写入设备时间线。

## 四、核心设计原则

| 原则 | 说明 |
|---|---|
| **全生命周期驱动** | 每台设备必须有清晰的「在途 → 已装机 → 运行中 → 维保中 → 退机/报废」状态链路 |
| **一物一档** | 以序列号为唯一标识，建立设备 360° 档案，禁止重复建档 |
| **状态即业务语言** | 设备状态必须能直接指导销售和售后的下一步动作 |
| **位置可追踪** | 设备必须归属到客户（HCO）和科室，支持转科/转院记录 |
| **设备-试剂-服务一体** | 设备档案中必须能看到配套试剂、历史工单、服务记录 |
| **移动端优先现场** | 装机、巡检、报修等现场操作必须支持手机/企业微信完成 |

## 五、角色与权限

### 5.1 角色职责

| 角色 | 核心权限 | 系统操作 |
|---|---|---|
| **销售代表** | 查看本人负责客户的设备、录入新装机信息、申请设备调拨/退机 | 查看、新建、编辑（草稿）、申请调拨、申请退机 |
| **销售经理** | 审核本团队设备调拨/退机申请、查看团队设备覆盖 | 审核、查看、导出 |
| **售后工程师** | 维护设备维修/巡检记录、更新设备状态、录入现场照片 | 维修登记、状态更新、上传附件 |
| **设备管理员** | 维护设备主数据、处理重复设备合并、管理设备状态流转 | 编辑、合并、报废、删除（逻辑删除） |
| **商务运营** | 查看设备保有量、保修到期预警、投放设备 ROI 分析 | 查看、导出、配置预警规则 |
| **经销商账号** | 查看本公司相关客户的设备、录入代装机信息 | 查看、新建（受区域限制） |

### 5.2 数据可见性

| 角色 | 可见范围 |
|---|---|
| 销售代表 | 本人负责客户的设备 |
| 销售经理 | 本团队负责客户的设备 |
| 区域总监 | 本大区全部设备 |
| 售后工程师 | 本人服务过的设备、当前工单关联设备 |
| 设备管理员 | 全量设备，含草稿/待审批设备 |
| 商务运营 | 全量设备数据（用于分析和预警） |
| 经销商账号 | 本公司相关客户设备，价格/合同信息脱敏 |

## 六、设备状态定义

### 6.1 主状态

| 状态值 | 状态名称 | 说明 |
|---|---|---|
| 0 | 草稿 | 已录入但未提交审核，可继续编辑 |
| 1 | 在途 | 已采购/已发货，尚未完成装机验收 |
| 2 | 已装机 | 已完成装机验收，进入运行阶段 |
| 3 | 运行中 | 设备正常使用，无异常 |
| 4 | 维修中 | 存在未关闭的维修工单 |
| 5 | 闲置 | 设备已装机但长期未使用 |
| 6 | 调拨中 | 设备正在办理转科/转院手续 |
| 7 | 退机中 | 设备正在办理退机/回收手续 |
| 8 | 已报废 | 设备已报废或退机完成，流程闭环 |

### 6.2 状态标签颜色

| 状态 | 颜色 |
|---|---|
| 草稿 | 灰色 |
| 在途 | 蓝色 |
| 已装机 | 绿色 |
| 运行中 | 绿色 |
| 维修中 | 橙色 |
| 闲置 | 黄色 |
| 调拨中/退机中 | 紫色 |
| 已报废 | 深灰 |

### 7.3 页面布局设计理念（五层架构）

设备管理列表页采用自上而下的五层信息架构，让用户从全局指标逐步聚焦到单台设备：

| 层级 | 板块 | 用户心理 |
|---|---|---|
| 第一层：全局感知 | 统计卡片 | 「当前设备资产整体健康度如何？有多少在途、多少维修、多少保修快到期？」 |
| 第二层：范围选择 | Tab 分组 + 视图切换 + 新建按钮 | 「我要看哪类设备？用卡片概览还是表格扫描？是否需要新增设备？」 |
| 第三层：定位筛选 | 搜索/筛选栏 | 「怎么快速找到某台设备或某类设备？」 |
| 第四层：明细呈现 | 卡片网格 / 数据表格 | 「这台设备当前状态、位置、保修情况如何？」 |
| 第五层：分页浏览 | 分页组件 | 「如何浏览更多设备？」 |

### 7.5 视图切换

| 视图 | 展示形式 | 每页条数 | 适用场景 |
|---|---|---|---|
| 卡片视图 | 4 列卡片网格 | 8 条 | 设备数较少，做概览 |
| 列表视图 | 表格 | 12 条 | 设备数较多，快速扫描 |

**默认规则**：设备总数 ≤20 时默认卡片视图，>20 时默认列表视图。切换视图、切换 Tab、执行筛选后，自动重置到第 1 页。

## 十、核心业务流程

### 10.1 设备装机建档流程

**正常流程**

1. 触发：设备到货或意向成交后，有权限的用户（销售代表/售后工程师/商务运营）进入设备管理，点击「+ 新建设备」。
2. 录入：选择客户与科室，填写品牌、型号、序列号、设备名称、投放模式、装机日期、保修截止日期、保修类型、负责人等字段。
3. 前端校验：校验必填项、字段格式（序列号长度、日期逻辑、枚举值等）；未通过则字段红字提示并阻止提交。
4. 提交保存：系统校验序列号全局唯一性；若配置审批（如大额 TP 设备），状态置为「草稿」或「在途」并进入审批流。
5. 归档同步：保存成功后状态为「已装机」，写入客户 360° 设备地图，同步关联意向状态为「已成交/已装机」，生成设备时间线首条记录。

**异常分支**

- E1 序列号重复：后端返回「序列号已存在」，前端弹窗提示「该序列号已建档，请检查或合并」，并提供「查看已有设备」入口。
- E2 客户/科室不存在：若选择的客户下无目标科室，提示「科室不存在，是否新增科室？」；点击后跳转新建科室或刷新科室列表。
- E3 网络超时/提交失败：提交超过 5 秒未响应，停止 Loading 并提示「网络超时，请稍后重试」；保留表单草稿，支持重试。
- E4 并发保存冲突：同一序列号被多人同时提交，后者提示「该设备刚被他人建档，请刷新后处理」，放弃当前提交。
- E5 权限不足：用户尝试为无权限客户创建设备时，「选择客户」下拉隐藏该客户，或提交时返回「无权限操作」并清空表单。

### 10.2 设备保修预警与续保流程

**正常流程**

1. 扫描：系统每日定时任务扫描所有设备的「保修截止日期」。
2. 命中：筛选出 90/60/30/7 天内到期的设备，生成对应的预警记录。
3. 推送：按规则向设备负责人、销售经理、商务运营推送预警消息（消息中心/企业微信/邮件，可配置）。
4. 处理：负责人在设备详情页点击「续保」，选择续保类型并创建续保意向或售后服务单。
5. 回填：续保完成后，更新设备的保修截止日期与保修类型，记录续保时间线，并取消对应预警。

**异常分支**

- E1 预警重复：同一设备在同一预警档位下，每日仅生成一条预警，避免重复打扰。
- E2 负责人缺失：负责人离职/调岗且无接替人时，预警自动升级推送给销售经理。
- E3 续保日期回填冲突：多人同时编辑保修信息，后者提交时提示「信息已被更新，请刷新后确认」，展示差异后选择覆盖或放弃。
- E4 网络超时：续保单保存超时，保留表单草稿并提示重试；已生成工单但未回写状态时，提供手动同步入口。
- E5 重复续保：系统检测到保修截止日期已更新且仍在有效期内，提示「该设备已续保，请勿重复操作」。

### 10.3 设备维修与状态变更流程

**正常流程**

1. 报修：设备出现故障，销售/售后/客户在有权限的前提下发起报修，系统校验设备当前状态是否允许报修。
2. 状态变更：创建售后工单后，系统自动将设备状态置为「维修中」；维修中设备在列表与详情页显示橙色状态标签。
3. 维修：售后工程师上门，记录维修内容、更换配件、工时、现场照片与验收结论。
4. 关单：维修完成后关闭工单，系统根据维修结果更新设备状态。
5. 归档：若设备可正常使用，状态恢复为「运行中」；若无法修复或达到报废标准，流程转入 10.5 设备退机/报废流程。

**异常分支**

- E1 状态冲突：设备处于「调拨中/退机中/已报废」时不可报修，提示「设备当前处于 XX 流程，请先处理完成后再报修」。
- E2 并发工单：同一设备存在多个未关闭工单时，状态保持「维修中」；最后一个工单关闭后，系统才恢复为「运行中」。
- E3 关单超时/网络失败：关闭工单请求超时，保留工单状态为「处理中」并提示重试；避免设备状态错误流转。
- E4 配件库存不足：工程师提交配件更换记录时，若配件库存不足，提示「配件库存不足，请联系仓库调拨」。
- E5 报废条件触发：维修结论为「无法修复」时，系统推荐发起报废申请；用户可一键跳转 10.5。

### 10.4 设备调拨流程

**正常流程**

1. 发起：销售代表或设备管理员在设备详情页点击「调拨」，选择申请类型（转科/转院）。
2. 填写：根据申请类型填写目标科室或目标医院、调拨原因、附件等；前端校验条件必填项与字段格式。
3. 提交：提交后设备状态变为「调拨中」，申请进入审批中心，原位置信息保留在历史记录中。
4. 审批：销售经理/设备管理员审批；驳回则退回申请人并恢复设备原状态，通过则更新客户/科室/位置备注。
5. 归档：系统记录调拨历史，生成时间线，设备状态根据业务规则变为「已装机」或「运行中」。

**异常分支**

- E1 目标无效：目标科室不存在或目标医院不在权限范围内，提示「目标无效，请重新选择或联系管理员」。
- E2 流程冲突：调拨审批期间设备被其他人报修或发起退机，提示「设备当前处于调拨流程中，请先完成调拨或撤销申请」。
- E3 审批超时：审批人超过 3 个工作日未处理，系统自动发送催办消息；超过 5 个工作日可配置升级至上级。
- E4 并发审批冲突：多人同时审批同一申请，后者提示「该申请已被处理，请刷新列表」，避免重复操作。
- E5 网络失败导致状态未更新：审批通过后写入设备主数据失败，触发补偿重试；若持续失败，通知设备管理员人工处理。

### 10.5 设备退机/报废流程

**正常流程**

1. 发起：销售代表、售后工程师或设备管理员在设备详情页发起退机或报废申请。
2. 填写：填写申请原因，上传退机签收单或报废证明；报废申请必须上传报废证明或退机签收单。
3. 提交：提交后设备状态变为「退机中」，申请进入审批中心。
4. 审批：销售经理初审 → 设备管理员终审（报废可配置财务节点）；任一节点驳回则退回申请人并恢复设备原状态。
5. 归档：终审通过后，设备状态变为「已报废」，从活跃列表移除并进入报废台账，关联试剂消耗停止计入活跃设备统计。

**异常分支**

- E1 附件缺失/格式错误：报废/退机未上传必填附件，或文件格式/大小不符，表单校验阻止提交并红字提示。
- E2 流程冲突：审批期间设备被报修或调拨，提示「设备状态已变化，请刷新后重新评估是否继续报废」。
- E3 归档失败：终审通过后写入报废台账或更新统计失败，触发补偿重试；若重试仍失败，通知设备管理员人工处理并记录告警日志。
- E4 重复申请：同一设备存在未完结的退机/报废/调拨申请时，禁止再次提交，提示「该设备已有未完结申请，请勿重复提交」。
- E5 报废后恢复：已报废设备原则上不可恢复；如确需撤销，需设备管理员在后台发起「撤销报废」流程并重新审批。

## 十一、交互设计要点

### 11.1 搜索筛选

- 顶部搜索框支持按设备名称、序列号、客户名称模糊搜索，回车或失焦触发。
- 筛选器支持品牌、型号、科室、状态、装机日期范围组合筛选。
- 筛选结果实时更新，同时重置分页到第 1 页。
- 支持保存常用筛选视图，如「我负责的三甲医院血球仪」。

### 11.2 视图切换

- 提供「列表视图」/「卡片视图」按钮组。
- 设备总数 ≤20 默认卡片视图，>20 默认列表视图。

| 批量导入失败 | 模板字段缺失/格式错误/序列号重复/无权限 | 给出错误文件下载，逐行列明错误原因及行号 | 用户修正后重新上传；部分成功时支持「仅导入正确行」或「全部回滚」 |

## 十三、核心设计原则与要点

1. **序列号是设备唯一身份证**：所有设备以序列号为唯一标识，杜绝重复建档；录入时必须校验唯一性。
2. **状态流转必须留痕**：设备每一次状态变更（装机、维修、调拨、报废）都必须记录变更人、变更时间、变更原因。
3. **保修是收入入口**：把保修到期预警前置到 90 天，驱动续保/升级意向，避免保修空窗。
4. **设备-试剂-服务三位一体**：设备详情必须能看到配套试剂消耗、历史工单、服务记录，打破数据孤岛。
5. **现场操作移动优先**：装机录入、报修、巡检等操作必须支持手机拍照、扫码序列号、离线暂存。
6. **TP/捐赠设备 ROI 可追踪**：对 TP/捐赠设备强制要求填写月预估试剂消耗，并与试剂运营模块联动，计算投放回报。
7. **报废不等于删除**：已报废设备保留完整档案，仅从高活跃列表移除，支持历史追溯和审计。
8. **跨业务状态同步**：设备状态变更要反向同步到客户 360° 设备地图、意向管理、售后工单等关联模块。

## 十四、与其它模块的关联

| 关联模块 | 数据流向/联动方式 |
|---|---|
| 客户 360° | 设备档案写入客户 360° 设备地图；客户 360° 中点击设备可进入设备详情 |

| 售后工单 | 设备报修时自动带入设备档案；工单状态变化同步更新设备状态为维修中/运行中 |
| 试剂运营 | 设备与配套试剂绑定，试剂消耗按设备聚合；设备利用率影响消耗预测 |

| 经营驾驶舱 | 设备保有量、保修到期预警、TP 设备 ROI 等数据汇入驾驶舱 |

| 经销商协同 | 经销商可代录代维设备，受区域和数据权限约束 |

## 十五、未考虑到的问题补充（开发者视角）

1. **序列号唯一性边界**：同一序列号在不同客户历史记录中可能出现（如先装机后退机再二次销售）。需明确唯一性校验是否仅针对「非报废」设备，还是全量历史。
2. **IoT 数据接入**：利用率、累计运行时长是否接入设备物联网数据？接入频率、数据质量异常如何处理？
3. **多科室共用设备**：部分设备可能跨科室使用，当前模型一台设备归属一个科室，是否需要支持「主科室 + 协同科室」？
4. **设备与合同的 1:N 关系**：一台设备可能由多个合同共同构成（销售合同 + 延保合同 + 维保合同），是否需要在设备下挂多个合同？
5. **保修日期变更场景**：延保、续保、保修重算时，保修截止日期的更新逻辑和审批流需要明确。
6. **设备图片与附件存储**：装机验收单、设备照片、报废证明等附件的存储策略、压缩规则、查看权限。
7. **历史数据迁移**：旧系统已有设备台账如何导入？重复序列号、缺失字段如何清洗？
8. **离线装机场景**：网络不稳定现场装机时，是否支持本地缓存、拍照暂存、联网后自动同步？
9. **与 ERP/财务系统对接**：设备资产编号、采购成本、折旧信息是否需要与 ERP/财务系统同步？
10. **批量操作**：是否支持批量导入设备、批量调拨、批量续保？批量导入模板和校验规则需要单独设计。
11. **报废设备的报表口径**：报废设备是否计入保有量？是否参与保修到期预警？需要在指标定义中明确。
12. **设备状态与工单状态的并发**：当多个工单同时关联一台设备时，如何避免状态冲突？
13. **经销商设备的回收**：经销商代管设备在合作终止时，数据归属和可见性如何切换？
14. **权限变更后的数据可见性**：负责人调岗或离职，设备负责人批量转移的流程是否需要支持？
