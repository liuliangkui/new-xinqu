# XQCOP 后端复用性提升开发计划

> 目标：把当前“模块化单体”逐步演进为“可复用的双中台架构”，实现从代码级复用 → 能力级复用 → 系统级复用。
>
> 原则：先抽象、后拆分；先技术中台、后业务中台；按模块逐步迁移，不中断现有业务开发。

---

## 一、总体演进路线

```
阶段 0：现状诊断与基线建立
阶段 1：基础治理与边界清晰化（2-3 周）
阶段 2：技术中台能力抽取（4-6 周）
阶段 3：业务中台能力抽象（6-8 周）
阶段 4：服务化与平台化（4-6 周）
```

---

| 1.5 收敛公共 DTO/装饰器/工具 | 提升代码级复用            | 把散落在各模块的公共 DTO、装饰器、helper 收敛到 `common/` 或独立包                    | 《公共资产清单》 + 重构后的 common        | 无   | lint 通过、重复代码下降         | 改动面大           |

### 阶段 2：技术中台能力抽取（4-6 周）

| 任务                      | 目标              | 关键动作                                                                                                                                            | 交付物                                | 依赖 | 验收标准                                    | 风险                   |

| 2.1 工作流引擎中台化      | 流程能力可复用    | 将 `flowable` + `workflow-definition` + `approval` 的核心能力抽象为 `WorkflowEngineService`；暴露启动流程、完成任务、查询任务、驳回、会签等稳定 API | `packages/workflow-engine` 或独立服务 | 1.4  | approval/workflow-definition 只依赖中台 API | 流程状态与业务状态同步 |
| 2.2 消息中心中台化        | 消息能力可复用    | 将 `message` 模块抽象为 `MessageCenterService`；支持站内信、短信、邮件、企微/钉钉统一发送接口                                                       | `packages/message-center` 或独立服务  | 1.4  | 所有消息发送走消息中心                      | 第三方通道不稳定       |
| 2.3 文件/对象存储中心     | 统一文件能力      | 新建 `file-center` 模块，封装 MinIO/OSS 上传、下载、预览、临时 URL；提供文件元数据管理                                                              | `packages/file-center`                | 无   | 附件、合同、图片统一走文件中心              | 大文件上传性能         |
| 2.4 权限与用户中心（IAM） | 身份/权限能力复用 | 将 `auth` + `user` + 数据权限抽象为 IAM 服务；提供用户、角色、部门、数据范围、JWT 校验 API                                                          | `packages/iam` 或独立服务             | 1.1  | 所有模块通过 IAM 校验，不直接查 user 表     | 性能瓶颈               |
| 2.5 搜索引擎中心          | 统一搜索能力      | 按《搜索引擎设计规范》实现 `search-gateway`；先接 PostgreSQL tsvector，后续可切 ES                                                                  | `packages/search-engine`              | 2.4  | 客户/线索/意向等搜索走搜索中心              | 索引一致性             |
| 2.6 规则引擎中心（轻量）  | 通用规则能力      | 提取冲突检测、健康度评分、SLA 计算等规则；支持 DSL 或脚本配置                                                                                       | `packages/rule-engine`                | 无   | 至少 2 个业务场景接入                       | 规则复杂度高           |

## 三、推荐实施节奏

| 阶段   | 建议启动时机                             | 优先级     |
| ------ | ---------------------------------------- | ---------- |
| 阶段 0 | 立即                                     | ⭐⭐⭐⭐⭐ |
| 阶段 1 | 阶段 0 完成后立即启动                    | ⭐⭐⭐⭐⭐ |
| 阶段 2 | 阶段 1 完成 60% 后启动，可并行           | ⭐⭐⭐⭐⭐ |
| 阶段 3 | 阶段 2 完成 50% 后启动，按业务优先级分批 | ⭐⭐⭐⭐   |
| 阶段 4 | 业务中台稳定后再启动                     | ⭐⭐⭐     |

> **建议**：不要一次性做完。先做完阶段 0-1，让代码边界清晰；然后优先把 **工作流引擎、消息中心、文件中心、IAM** 这 4 个技术中台抽出来，收益最大、风险最低。

## 五、风险提示

1. **不要为了复用而过度抽象**：先确认该能力确实会被多个模块/系统复用，再抽取。
2. **数据库拆分要谨慎**：一域一 Schema 可以先行，真正分库分表要在业务稳定后。
3. **事件驱动引入幂等、顺序、补偿**：需要配套 Saga 或事务消息机制。
4. **团队学习成本**：DDD、事件驱动、微服务运维都需要培训和实践。
