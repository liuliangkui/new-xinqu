# 鑫渠高保真原型 → 完整系统开发方案

## 1. 目标与约束

### 1.1 目标
基于现有高保真 HTML 原型，建设一套前后端完整、可投产的企业级 CRM/业务协同系统。

### 1.2 核心约束
- **界面框架不变**：原型的视觉、布局、交互、组件样式必须 1:1 还原到 Vue 体系中。
- **技术栈继承**：优先复用当前已搭建的 `Vue 3 + Vite + TypeScript + Ant Design Vue + Tailwind CSS 4 + Pinia` 前端栈。
- **逐步替换**：按模块逐个从原型迁移到真实页面，避免一次性重写带来的进度与质量风险。

---

## 2. 总体技术栈

| 层级 | 技术选型 | 说明 |
|---|---|---|
| 前端框架 | Vue 3 + Vite + TypeScript | 当前已具备，保持不变 |
| UI 组件库 | Ant Design Vue 4 + 自研 `Xq` 组件库 | 复杂组件用 AntDV，业务组件自研 |
| 样式方案 | Tailwind CSS 4 | 当前已具备 |
| 状态管理 | Pinia | 按业务域拆分 Store |

| 主数据库 | PostgreSQL 16 | 关系型数据复杂，PG 更适合 |
| 缓存/会话/队列 | Redis 7 | 缓存、分布式会话、BullMQ 队列 |
| 消息队列 | BullMQ（基于 Redis） | 异步任务、审批通知、报表生成 |

## 3. 前端改造方案

### 3.1 迁移原则

原型是一个包含 22+ 业务模块的单文件 HTML，约 2.4 万行，内部通过 `switchView()` 做模块级切换。迁移时遵循以下原则：

| 原则 | 说明 |
|---|---|
| DOM 结构不动 | 将原型中每个模块的 HTML 直接迁移到对应 `src/views/xxx/index.vue` 的 `<template>`，class、id、事件先保留 |
| 样式不动 | 内联样式、Tailwind class、自定义 CSS 全部迁移，确保像素级一致 |
| 交互行为组件化 | 将 `switchView`、`switchPerformanceTab`、`openModal` 等逻辑改为 Vue 的 `ref/computed/method` |
| 数据接口化 | 硬编码数据替换为 `api.getXxx()`，未接入后端时通过 MSW 走 mock |
| 响应式保留 | 每个页面必须同时验证桌面端与移动端布局 |

### 3.2 组件库补全

当前已有组件：`XqTimeline`、`XqDataTable`、`XqCardGrid`、`XqDrawer`、`XqKpiCard` 等。需继续补充以下业务组件：

- `XqRankList`：排名列表（绩效 Top5、区域排名）
- `XqFunnelChart`：销售漏斗图
- `XqGaugeChart`：达成率仪表盘
- `XqTrendChart`：折线/柱状趋势图
- `XqModalCard`：统一卡片式弹窗（参考客户 360 风格）
- `XqAccordionList`：列表视图手风琴下拉面板
- `XqFilterPanel`：通用筛选栏
- `XqEmptyState`：空状态
- `XqLoadingSkeleton`：加载骨架屏
- `XqStatusBadge`：状态标签
- `XqAvatarGroup`：人员头像组

所有组件的 Props 与 Slot 设计必须能 1:1 还原原型中的元素。

### 4.3 权限模型

采用 **RBAC + 数据范围** 双维度控制：

- **RBAC**：角色（超管、区域经理、销售代表、经销商、售后工程师等）绑定菜单权限与按钮权限
- **数据范围**：
  - 仅本人
  - 本部门及下级
  - 本区域
  - 全部

通过 NestJS Guard + Prisma middleware 在每次查询前注入 `where` 条件，统一控制数据可见性。

### 4.4 工作流引擎

审批中心与流程设计器需要工作流能力，提供两种方案：

| 方案 | 选型 | 适用场景 |
|---|---|---|
| A（推荐） | Camunda / Flowable | 流程复杂、需要 BPMN 可视化设计器、长期演进 |
| B（轻量自研） | 自建 `FlowDefinition / FlowNode / FlowInstance / FlowTask` | 当前审批场景较简单，快速落地 |

建议先用 **方案 B** 跑通审批、工单流转，后续若流程复杂度上升再迁移至 **方案 A**。

### 4.5 驾驶舱与业绩计算

- 每晚通过 NestJS Schedule + BullMQ 聚合业绩数据到 `Performance` 表，避免大屏实时查询拖垮数据库。
- 销售漏斗、区域经营、大单作战室等分析型数据使用物化视图或 Elasticsearch 聚合。
- 预警规则（维保到期、库存预警、合规到期、业绩缺口）通过 BullMQ 延迟队列触发。

### 4.6 文件与附件

- 上传接口：`POST /api/file/upload`
- 存储：MinIO（开发/测试）、阿里云 OSS（生产）
- 数据库只保存文件 key 与元数据
- 前端预览：图片/PDF 直接访问 CDN URL

## 6. 关键落地原则

1. **界面不漂移**
   - 每个 Vue 页面开发完成后，与原型 HTML 同分辨率截图对比。
   - 引入视觉回归测试（Playwright + pixelmatch），锁住关键页面像素差异。

2. **接口先行**
   - 每个模块开发前，先确定 OpenAPI 契约，前后端再并行开发。

3. **Mock 平滑切换**
   - 开发环境无后端时自动走 MSW mock。
   - 接入后端后通过环境变量 `VITE_API_BASE_URL` 切换。

4. **数据一致性**
   - 线索、意向、客户、绩效等核心实体统一 ID、状态机、字典值。
   - 禁止前端硬编码业务状态。

5. **移动端保留**
   - 原型中已有移动端视图，所有页面开发时必须同时验证响应式。

6. **测试左移**
   - 单元测试：Vitest + Vue Test Utils
   - 接口测试：NestJS e2e + Supertest
   - 端到端测试：Playwright

## 8. 100% 还原保障体系

要确保最终系统效果 100% 接近原型，必须建立一套**可量化、可验证、可追责**的还原保障体系，而不是依赖开发人员的自觉性。

### 8.1 原型冻结：唯一设计源

- 选定当前 `鑫渠高保真原型.html` 的某个 Git 版本作为**唯一设计源**，任何开发、测试、验收都基于此版本。
- 进入开发阶段后，原则上不再直接修改原型；任何界面调整必须走「设计变更单」，同步更新原型和开发页面。
- 每次迭代前，先确认原型基线版本，避免「开发看的是 A 版，验收按 B 版」的混乱。

### 8.2 设计 Token 100% 对齐

从原型中提取所有颜色、字号、间距、圆角、阴影，固化成 Token，开发中禁止硬编码。

```css
/* src/styles/tokens.css */
:root {
  --color-primary: #3370FF;
  --color-success: #34C724;
  --color-warning: #FF7D00;
  --color-danger: #F53F3F;
  --color-ink: #1F2329;
  --color-sub: #6B7280;
  --color-line: #E5E7EB;
  --text-xs: 12px;
  --text-sm: 14px;
  --text-base: 16px;
  --space-1: 4px;
  --space-2: 8px;
  --radius-md: 8px;
  --radius-lg: 12px;
}
```

在 `tailwind.config.ts` 中扩展这些 Token，并通过 Stylelint 禁止硬编码颜色和尺寸。

### 8.3 组件级 1:1 还原

把原型中重复出现的 UI 元素拆解为组件，每个组件必须有原型截图对照：

| 组件名 | 原型位置 | 截图文件 |
|---|---|---|
| XqKpiCard | 经营驾驶舱 KPI 区 | `design/kpi-card.png` |
| XqRankList | 绩效 Top5 | `design/rank-list.png` |
| XqFunnelChart | 销售漏斗 | `design/funnel-chart.png` |
| XqModalCard | 客户 360 弹窗 | `design/modal-card.png` |
| XqAccordionList | 列表视图手风琴 | `design/accordion-list.png` |
| XqDataTable | 线索/工单列表 | `design/data-table.png` |

每个组件开发完成后，将其截图与原型的组件截图用 pixelmatch 对比，差异率必须 < 0.1%。

### 8.4 页面级视觉回归测试

使用 Playwright 对每个页面进行截图，并与原型基线图对比：

```ts
// tests/visual/performance.spec.ts
import { test, expect } from '@playwright/test';

test('目标绩效页面视觉还原', async ({ page }) => {
  await page.goto('/performance');
  await page.waitForLoadState('networkidle');
  const screenshot = await page.screenshot({ fullPage: true });
  expect(screenshot).toMatchSnapshot('prototype-performance.png', {
    threshold: 0.1,
    maxDiffPixels: 100,
  });
});
```

必须覆盖以下分辨率：
- 桌面大屏：1920×1080
- 桌面中屏：1440×900
- 笔记本：1366×768
- 平板：768×1024
- 手机：375×812

原型基线图通过 Playwright 对 `鑫渠高保真原型.html` 在相同分辨率下截图生成，保存为 `tests/visual/snapshots/prototype-*.png`。

### 8.5 交互还原 Checklist

每个页面开发前输出《交互事件清单》，开发后逐条验证：

| 页面 | 元素 | 事件 | 原型行为 | 状态 |
|---|---|---|---|---|
| 绩效 | 我的绩效 Tab | click | 切换为网格视图，显示 3 条数据 | ✅ |
| 绩效 | chart 视图按钮 | click | 显示对应维度排名 | ✅ |
| 线索 | 卡片 | click | 弹出卡片弹窗，显示线索详情 | ⬜ |
| 线索 | 列表行 | click | 手风琴展开详情面板 | ⬜ |

产品经理或设计人员拿着清单逐条点击验证，重点检查弹窗动画、Tab 切换、筛选结果、空状态、加载状态、错误提示。

### 8.6 开发规范约束

- **DOM 结构尽量不动**：优先保持原型的 DOM 层级和 class 名，减少结构变化导致的样式漂移。
- **样式隔离**：每个页面使用 `<style scoped>`，公共样式通过 Token 引用。
- **禁止擅自优化**：不得以「更好看」「更简洁」为由修改原型设计；任何与原型不一致的地方必须有变更单背书。
- **ESLint/Stylelint**：禁止硬编码颜色、字号、间距，强制使用 Token。

### 8.7 三级验收机制

| 级别 | 负责人 | 内容 | 通过标准 |
|---|---|---|---|
| 开发自测 | 前端开发 | 截图对比 + 交互清单 | 视觉差异 < 0.1%，交互清单 100% 完成 |
| 设计/产品走查 | 产品经理/设计 | 对照原型逐页验收 | 无视觉和交互偏差 |
| 视觉回归 CI | 自动化 | Playwright 多分辨率截图 | 所有页面通过快照对比 |
| 业务确认 | 业务方 | 关键业务流程验证 | 业务逻辑与原型一致 |

### 8.8 差异处理 SOP

发现开发页面与原型不一致时：

1. **定位**：截图对比找出差异区域。
2. **定责**：判断是开发偏离、原型问题还是合理优化。
3. **修复**：开发按原型修改，或走变更单更新原型。
4. **复测**：重新跑视觉回归和交互清单。
5. **归档**：把差异原因记录到《还原问题库》，避免重复犯错。

### 8.9 工具链清单

| 用途 | 工具 |
|---|---|
| 原型截图 | Playwright / Puppeteer |
| 视觉对比 | Playwright toMatchSnapshot / pixelmatch |
| 组件展示 | Storybook |
| Token 管理 | Style Dictionary / CSS Variables |
| 样式检查 | Stylelint |
| 交互录屏 | Screenity / OBS |
| 设计标注 | Figma / 即时设计（可选） |

### 8.10 关键成功指标

- **视觉差异率**：所有页面截图对比差异 < 0.1%。
- **交互覆盖率**：原型中所有可点击元素 100% 实现。
- **Token 合规率**：代码扫描中硬编码样式为 0。
- **视觉回归通过率**：CI 中 100% 通过。
- **设计走查通过率**：产品/设计走查一次性通过 > 90%。

## A. 前端选型

### A.1 Vue 3

**推荐理由：**

- **项目现状完全匹配**：当前 `package.json` 已经是 `vue@^3.5.40`、`vue-router@^5.2.0`、`pinia@^4.0.2`，继续用 Vue 3 没有迁移成本。
- **渐进式框架，适合企业后台**：CRM/业务系统以表单、表格、弹窗、审批流为主，Vue 的选项式/组合式 API 都能快速写出可读性高的业务代码。
- **模板语法更贴近 HTML**：原型本身就是大量 HTML，迁移到 Vue 的 `<template>` 时，DOM 结构和 class 基本可以原样保留，这是 React JSX 无法比拟的优势。
- **中文文档与社区**：国内 Vue 生态成熟，Ant Design Vue、Element Plus、Naive UI 均有大量中文资料，招聘与排障成本更低。

**与 React 对比：**

| 维度 | Vue 3 | React 18 |
|---|---|---|
| 原型迁移成本 | 低，HTML 几乎可原样迁移 | 高，需改 JSX + 状态管理 |
| 学习曲线 | 平缓，模板语法直观 | 较陡，Hooks 心智负担重 |

| 类型体验 | 模板类型提示稍弱 | TSX 类型更强 |
| 团队现状 | 已具备 | 需重新培训 |

**结论**：保持 Vue 3 是成本最低、风险最小的选择。

### A.2 Vite

**推荐理由：**

- **当前项目已用 Vite 8**：无需更换构建工具。

**与 Webpack 对比：**

| 维度 | Vite | Webpack |

| 启动速度 | 快（秒级） | 慢（分钟级，大项目） |
| 配置复杂度 | 低 | 高 |
| 生态成熟度 | 已非常成熟 | 更成熟但复杂 |
| 团队现状 | 已具备 | 需迁移配置 |

### A.3 TypeScript

- **大型项目必需**：22 个模块、数百个接口，没有类型约束后期维护成本极高。
- **IDE 体验**：自动补全、重构、类型检查能显著减少低级错误。
- **当前项目已配置**：`vue-tsc`、`@tsconfig/node24` 都已存在。

### A.4 Ant Design Vue 4

**推荐理由：**

- **企业级组件库**：表格、表单、树、穿梭框、级联选择、日期范围等复杂组件开箱即用。
- **与 Tailwind 互补**：AntDV 负责复杂交互组件，Tailwind 负责布局与原子样式。
- **当前项目已依赖**：`ant-design-vue@^4.2.6`，无需引入新库。
- **设计规范统一**：自带 Design Token，方便做主题定制。

**与 Element Plus / Naive UI 对比：**

| 维度 | Ant Design Vue | Element Plus | Naive UI |
|---|---|---|---|
| 企业后台组件丰富度 | 非常丰富 | 丰富 | 中等 |
| 表格性能 | 强 | 强 | 中等 |
| 主题定制 | Design Token | CSS Var | CSS Var |
| 当前项目 | 已使用 | 未使用 | 未使用 |
| 社区活跃度 | 高 | 高 | 中等 |

### A.5 Tailwind CSS 4

**推荐理由：**

- **原型大量使用了 Tailwind class**：迁移时可以直接复用，不需要重写 CSS。
- **原子化样式适合快速还原高保真**：颜色、间距、圆角、阴影等通过 class 直接控制，开发效率高。
- **与 Vue scoped style 配合好**：可以只在需要的地方使用 Tailwind，复杂样式再写自定义 CSS。

- **Vue 官方推荐状态管理库**：Vuex 已停止主动维护，Pinia 是未来。

- **模块化设计**：按业务域拆分 Store，避免单文件臃肿。
- **Devtools 支持好**：时间旅行、状态快照方便调试。

## B. 后端选型

### B.1 NestJS 11 + TypeScript

**核心推荐理由：**

- **与前端同栈，降低团队成本**：前后端都用 TypeScript，可以共享类型定义、工具函数、枚举值，减少沟通成本。
- **架构清晰，适合大型项目**：模块（Module）、控制器（Controller）、服务（Service）、守卫（Guard）、拦截器（Interceptor）、管道（Pipe）分层明确，22 个业务模块可以并行开发而不互相污染。
- **依赖注入成熟**：服务之间解耦，测试容易。
- **生态丰富**：与 Prisma、TypeORM、BullMQ、Redis、Passport、Swagger 集成都有官方或社区支持。
- **自带 OpenAPI/Swagger**：通过装饰器自动生成 `openapi.json`，前端可直接生成 TS 类型。
- **企业级特性内置**：异常过滤器、日志、校验、序列化、限流、缓存都有现成方案。

**与 Spring Boot 对比：**

| 维度 | NestJS + TS | Spring Boot 3 |
|---|---|---|
| 与前端技术栈一致性 | 高（同 TS 生态） | 低（Java 生态） |
| 开发效率 | 高，语法简洁 | 高，生态极其成熟 |
| 企业级生态 | 成熟 | 极其成熟 |
| 国内招聘 | Node 人才相对少 | Java 人才充足 |
| 长期维护 | 适合中型系统 | 适合大型/超大型系统 |
| 微服务支持 | 支持 | 更成熟 |
| 部署资源占用 | 较低 | 较高 |

**结论**：如果团队已有 Java 能力且预期系统非常庞大，可选 Spring Boot；否则 NestJS 能以更低成本快速落地，且与本项目前端栈最匹配。

**与 Express / Koa / Fastify 对比：**

| 维度 | NestJS | Express | Koa | Fastify |
|---|---|---|---|---|
| 架构约束 | 强（规范清晰） | 弱（自由） | 弱（自由） | 弱（自由） |
| 大型项目可维护性 | 高 | 中低 | 中低 | 中 |
| 插件生态 | 非常丰富 | 丰富 | 中等 | 增长中 |
| 学习成本 | 中 | 低 | 低 | 低 |
| 性能 | 中（底层可用 Fastify） | 中 | 高 | 高 |

**结论**：Express/Koa 适合小型服务或微服务网关，22 个业务模块的 CRM 系统需要 NestJS 这样的框架约束。

### B.2 Prisma 6

**推荐理由：**

- **类型安全**：Prisma Client 根据 schema 自动生成 TS 类型，前后端可共享。
- **迁移管理**：`prisma migrate` 让数据库 schema 变更可追踪、可回滚。
- **查询性能可控**：支持关系查询、聚合、原生 SQL，复杂场景可写 `$queryRaw`。
- **VS Code 插件强**：自动补全、格式化、语法高亮。
- **与 NestJS 集成成熟**：`@nestjs/config` + `PrismaService` 模式社区广泛使用。

**与 TypeORM / Sequelize 对比：**

| 维度 | Prisma | TypeORM | Sequelize |
|---|---|---|---|
| 类型安全 | 极强（生成式） | 中等（装饰器） | 弱 |
| 学习曲线 | 中 | 中 | 低 |
| 迁移工具 | 优秀 | 一般 | 一般 |
| 复杂查询灵活性 | 中等（可用 raw） | 高 | 高 |
| 与 TS/NestJS 集成 | 优秀 | 良好 | 一般 |
| 社区趋势 | 增长快 | 稳定 | 下降 |

**结论**：TypeORM 灵活性更高，但 Prisma 的类型安全和迁移体验对中型团队更友好。

## C. 数据库与存储选型

### C.1 PostgreSQL 16

**推荐理由：**

- **关系型数据复杂**：CRM 系统有大量客户、线索、意向、订单、工单、审批等关联，关系型数据库仍是最佳选择。
- **JSONB 支持**：PG 的 JSONB 可以灵活存储扩展字段（如客户自定义字段、表单数据），兼具关系型与部分文档型能力。
- **窗口函数与 CTE**：业绩排名、漏斗分析、同比环比等统计查询原生支持强。
- **全文检索**：内置 `tsvector`，中小规模可不依赖 Elasticsearch。
- **开源、稳定、生态成熟**：适合长期维护。

**与 MySQL 对比：**

| 维度 | PostgreSQL | MySQL 8 |
|---|---|---|
| 复杂查询能力 | 强（窗口函数、CTE、JSONB） | 中等 |
| 数据一致性 | 强 | 中等 |
| JSON 支持 | JSONB 更成熟 | JSON 功能较弱 |
| 国内云厂商支持 | 全面 | 全面 |
| 团队熟悉度 | 视团队而定 | 国内更熟悉 |

**结论**：两者都能用。PG 在复杂统计和扩展字段上更优，适合 CRM 分析型场景。

**与 MongoDB 对比：**

MongoDB 适合文档结构多变、关联少的场景。CRM 有强关联和复杂事务，不推荐作为主库，但可用于日志、埋点等辅助场景。

### C.2 Redis 7 + BullMQ

**Redis 推荐理由：**

- **一物多用**：会话存储、接口缓存、热点数据缓存、分布式锁、限流计数器。
- **性能极高**：内存操作，适合高频读取场景（如字典、用户权限）。
- **与 NestJS 集成简单**：`@nestjs/cache-manager`、`ioredis` 都有成熟方案。

**BullMQ 推荐理由：**

- **基于 Redis**：不需要额外部署消息队列中间件。
- **延迟队列**：维保到期提醒、合规到期提醒、业绩预警等场景天然适合。
- **重试与死信**：任务失败可自动重试，失败过多进入死信队列。
- **与 NestJS 官方集成**：`@nestjs/bullmq` 提供装饰器式 API。

**与 RabbitMQ / Kafka 对比：**

| 维度 | BullMQ | RabbitMQ | Kafka |
|---|---|---|---|
| 部署复杂度 | 低（复用 Redis） | 中 | 高 |
| 实时性 | 高 | 高 | 高 |
| 消息持久化 | 依赖 Redis | 强 | 极强 |
| 吞吐量 | 中高 | 高 | 极高 |
| 适用场景 | 任务队列、延迟任务 | 企业总线 | 大数据流处理 |

**结论**：当前业务量级用 BullMQ 足够，未来若数据量暴涨再引入 Kafka。

### C.3 文件存储：MinIO（开发/测试）+ 阿里云 OSS（生产）

**MinIO 推荐理由：**

- **S3 兼容**：代码中只需换 endpoint，即可从 MinIO 切到阿里云/腾讯云/AWS。
- **本地开发友好**：Docker 一键启动，不依赖外网。
- **免费开源**：测试环境无成本。

**阿里云 OSS 推荐理由：**

- **国内访问快**：CDN 节点多，适合国内用户。
- **安全稳定**：支持防盗链、HTTPS、生命周期管理。
- **与阿里云生态整合**：若未来用阿里云 ECS/RDS，管理更方便。

### C.4 Elasticsearch（可选）

**推荐理由：**

- 客户名称、线索电话、工单描述、合同内容等需要模糊搜索。
- PG 的 `tsvector` 在十万级数据内够用，超过百万级建议引入 ES。
- 可先做 PG 全文检索，等数据量上来后再平滑迁移到 ES。

**引入时机：**

- 数据量 < 50 万：PG `LIKE` + `tsvector`。
- 数据量 50 万 ~ 200 万：PG 全文检索 + 简单 ES。
- 数据量 > 200 万或搜索复杂：必须引入 ES。

## D. 部署与运维选型

### D.1 Docker + docker-compose（开发/测试）

**推荐理由：**

- **开发环境一致性**：新成员 `docker-compose up` 即可跑起前端、后端、数据库、Redis、MinIO。

- **生产级编排**：服务发现、负载均衡、自动扩缩容、滚动更新、健康检查。

- **云厂商支持好**：阿里云 ACK、腾讯云 TKE、AWS EKS 均成熟。

| 维度 | Docker + K8s | 传统单机部署 | Serverless |

| 长期演进 | 强 | 弱 | 中 |
| 适合阶段 | 生产 | 开发/极小型 | 流量波动大 |

## F. 风险与应对

| 风险 | 应对 |
|---|---|
| 原型 HTML 迁移工作量大 | 按模块拆分，优先核心模块；复杂页面先做视觉回归锁定 |
| NestJS 团队不熟悉 | 先做培训 + 搭建脚手架；复杂业务用成熟示例复用 |
| 数据库设计返工 | 核心实体（用户、客户、线索、意向）先定版，预留扩展字段 |
| 性能瓶颈 | 先 PG 优化 + 缓存；指标不达标再引入 ES、分库分表 |
| 第三方集成（企业微信/钉钉） | 预留 webhook 与消息推送接口，后期逐个对接 |
