## 一、设计目标

1. **统一入口**：全局搜索框支持跨应用搜索，应用内搜索支持业务深度检索
2. **智能查询**：支持全文检索、模糊查询、拼音首字母、拼音全拼、智能联想
3. **权限感知**：不同角色只能搜到自己有权限的数据
4. **应用可定制**：每个应用可自定义搜索字段、权重、筛选条件、展示模板
5. **高性能**：搜索响应 < 500ms，支持 1000 并发
6. **可扩展**：新应用接入搜索只需配置，不修改引擎核心

### 2.1 全局搜索 vs 应用内搜索

| 维度 | 全局搜索 | 应用内搜索 |
|---|---|---|
| 入口位置 | 顶部导航栏 ⌘K | 应用列表页顶部 |
| 搜索范围 | 跨应用（客户、线索、意向、联系人等） | 当前应用数据 |
| 搜索字段 | 标题、名称、编号等核心字段 | 应用全部可搜索字段 |
| 筛选能力 | 按应用类型筛选 | 应用专属筛选条件 |
| 结果展示 | 分类聚合展示 | 列表/卡片展示 |
| 使用场景 | 快速定位任意对象 | 在应用内精确定位 |

## 三、搜索引擎选型

### 3.1 选型建议

推荐 **Elasticsearch 8.x**，理由：

| 能力 | 说明 |
|---|---|
| 全文检索 | 基于倒排索引，支持中文分词 IK |
| 模糊查询 | 支持 wildcard、fuzzy、prefix 查询 |
| 拼音搜索 | 通过自定义 analyzer 实现 |
| 聚合分析 | 支持按类型、状态、区域聚合统计 |
| 高亮 | 支持搜索结果关键词高亮 |
| 水平扩展 | 支持集群分片，满足 1000 并发 |
| 近实时 | 数据写入后 1 秒内可搜索 |

### 3.2 集群规划

| 节点类型 | 数量 | 配置 | 用途 |
|---|---|---|---|
| Master Node | 3 | 4C8G | 集群管理 |
| Data Node | 3 | 8C16G | 数据存储与查询 |
| Coordinator Node | 2 | 4C8G | 查询聚合、负载均衡 |

## 四、索引设计

### 4.1 索引划分

按业务对象类型划分索引，便于独立扩展和定制：

| 索引名 | 数据对象 | 主要字段 |
|---|---|---|
| idx_customer | 客户 | name, region, level, dept, owner, tags |
| idx_contact | 联系人 | name, phone, title, dept, hospital, role |
| idx_lead | 线索 | code, customer, dept, summary, source, owner |
| idx_opportunity | 意向 | title, customer, type, amount, stage, owner |
| idx_equipment | 设备 | code, model, hospital, dept, status |
| idx_ticket | 工单 | code, title, hospital, status, priority |
| idx_reagent | 试剂 | name, hospital, spec, brand |
| idx_document | 文档 | title, content, type, owner |

### 4.2 统一文档结构

每个索引文档包含通用字段：

```json
{
```

### 4.3 多字段映射策略

为支持多种查询方式，对核心字段建立多字段映射：

```json
{
  "mappings": {
    "properties": {
      "title": {
        "type": "text",
        "analyzer": "ik_smart",
        "fields": {
          "keyword": { "type": "keyword" },
          "pinyin": {
            "type": "text",
            "analyzer": "pinyin_analyzer"
          },
          "prefix": {
            "type": "text",
            "analyzer": "prefix_analyzer"
          }
        }
      },
      "keywords": {
        "type": "keyword"
      },
      "pinyinFirst": {
        "type": "keyword"
      }
    }
  }
}
```

## 五、查询能力设计

### 5.1 支持的查询方式

| 查询方式 | 示例 | 实现 |
|---|---|---|
| 全文检索 | "昆明 第一人民医院" | ik_smart 分词 + multi_match |
| 精确匹配 | "昆明市第一人民医院" | title.keyword |
| 前缀匹配 | "昆明" → "昆明市..." | title.prefix / edge_ngram |
| 模糊查询 | "昆名" → "昆明" | fuzzy 查询 |
| 拼音全拼 | "kunming" → "昆明" | pinyin_analyzer |
| 拼音首字母 | "km" → "昆明" | pinyinFirst.keyword |
| 编号搜索 | "L2026072801" | code.keyword |
| 手机号搜索 | "138****5678" | phone.keyword |
| 高级筛选 | 区域=云南 AND 等级=三甲 | bool query + filter |
| 智能联想 | 输入"昆"提示"昆明..." | suggest / completion |

### 5.2 查询解析策略

```
用户输入 "km 三甲"
    │
    ▼
判断输入类型：
    - 是否纯英文？→ 拼音查询
    - 是否首字母组合？→ 拼音首字母查询
    - 是否含特殊符号？→ 编号/手机号
    - 默认 → 中文分词查询
    │
    ▼
构建 multi_match 查询：
    title^3, keywords^2, pinyin^1.5, pinyinFirst^1
    │
    ▼
应用权限过滤 + 应用范围过滤
    │
    ▼
返回结果并按相关度排序
```

### 5.3 拼音分析器配置

```json
{
  "analysis": {
    "analyzer": {
      "pinyin_analyzer": {
        "tokenizer": "pinyin_tokenizer"
      }
    },
    "tokenizer": {
      "pinyin_tokenizer": {
        "type": "pinyin",
        "keep_separate_first_letter": true,
        "keep_full_pinyin": true,
        "keep_original": true,
        "limit_first_letter_length": 16,
        "lowercase": true,
        "remove_duplicated_term": true
      }
    }
  }
}
```

## 八、权限过滤

### 8.1 数据范围过滤

搜索时必须按用户数据范围过滤：

```json
{
  "query": {
    "bool": {
      "must": [
        { "multi_match": { "query": "昆明", "fields": ["title^3", "keywords^2"] } }
      ],
      "filter": [
        { "term": { "tenantId": "tenant_001" } },
        { 
          "bool": {
            "should": [
              { "term": { "permission.owner": "user_001" } },
              { "term": { "permission.dept": "dept_001" } },
              { "term": { "permission.region": "云南" } },
              { "term": { "permission.roles": "sales_director" } }
            ]
          }
        }
      ]
    }
  }
}
```

### 8.2 字段级权限

- 某些字段对特定角色不可见，搜索时排除或脱敏
- 例如：金额对普通售后不可见，搜索结果显示为「--」

## 十、数据同步

### 10.1 同步方式

| 方式 | 适用场景 | 延迟 |
|---|---|---|
| CDC（Debezium/Canal） | 核心业务数据 | < 1s |

| 定时全量同步 | 历史数据修复 | 天级 |
| 手动重建索引 | 索引升级、Mapping 变更 | 按需 |

### 10.2 同步流程

```
业务数据变更
    │
    ▼
发布领域事件 / CDC 捕获
    │
    ▼
数据同步服务
    │
    ▼
数据清洗、分词、拼音转换
    │
    ▼
写入 Elasticsearch 索引
```

## 十一、性能优化

### 11.1 查询优化

- 使用 `filter` 替代 `must` 做权限过滤，可利用缓存
- 限制返回字段，避免 `_source` 过大
- 分页深度限制，超过 10000 条使用 search_after
- 热点搜索词缓存 5 分钟

### 11.2 索引优化

- 合理设置分片数（建议 5 个主分片）
- 对高频查询字段加索引
- 定期合并段、清理旧索引
- 历史数据按时间归档到冷节点

### 11.3 前端优化

- 输入防抖 300ms
- 搜索结果分页加载
- 联想补全最多 10 条
- 首屏只加载必要字段

## 十三、完善建议

1. **搜索热词统计**：记录用户搜索热词，优化排序和推荐
2. **搜索无结果引导**：提示用户修改关键词或新建记录
3. **语音搜索**：移动端支持语音输入
4. **图片/OCR 搜索**：识别设备铭牌、合同图片中的文字
5. **语义搜索**：引入向量搜索，支持自然语言查询
6. **个性化排序**：根据用户历史行为调整结果排序
7. **搜索审计**：记录敏感数据搜索日志，满足合规要求

## 十四、与系统架构的关系

搜索引擎作为技术中台的核心能力，所有业务上下文通过**搜索网关**调用：

```
业务应用 ──▶ 搜索网关 ──▶ Elasticsearch
                │
                ▼
           权限引擎过滤
                │
                ▼
           返回结果
```

这样可以保证：
- 搜索逻辑统一维护
- 权限过滤统一处理
- 新应用接入成本低
