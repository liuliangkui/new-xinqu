## 一、协作模型定义

### 1.1 角色分工

| 角色 | 使用模型 | 核心职责 |
|---|---|---|
| 主控 agent | Claude 4 / Claude 3.7 Sonnet | 理解需求、拆解任务、准备上下文、调用 DeepSeek、验收结果、组装代码、最终负责 |
| 实现 agent | DeepSeek-V4 1M / DeepSeek-Coder-V2 | 在 Claude 给出的精确上下文内生成完整模块代码 |
| 验收 agent | Claude 3.5 Sonnet / 专用测试 agent | 独立运行测试、截图对比、代码审查 |

### 1.2 基本原则

1. **Claude 是最终责任人**：无论 DeepSeek 输出什么，Claude 必须验收通过才能进入代码库。
2. **一次一模块**：每次调用 DeepSeek 只处理一个应用模块或一个独立子任务，禁止一次性抛出整个系统。
3. **上下文必须完整**：调用 DeepSeek 时必须同时给出：设计文档 + 全局规范 + 组件库 + 字段规范 + 接口契约。
4. **输出必须可验证**：DeepSeek 返回的代码必须附带自测步骤，Claude 必须执行验证。
5. **失败必须回退**：如果 DeepSeek 输出连续两次无法通过验收，Claude 必须停止调用，改由人工介入或重新拆解任务。

## 二、Claude 调用 DeepSeek 的前提条件

在调用 DeepSeek 之前，Claude 必须完成以下检查，任何一项不满足都禁止调用：

| 检查项 | 通过标准 |
|---|---|
| 设计文档已就绪 | 对应模块的「功能与交互说明.md」已通过《鑫渠应用文档验收标准.md》v1.1 自检，总分 >= 135 分 |
| 全局规范已明确 | 已确认技术栈、组件库、响应式断点、样式变量、权限模型 |
| 接口契约已确定 | 已输出或确认该模块的 `types.ts` + `api.ts` |
| 依赖模块已明确 | 已列出该模块依赖的其它模块、组件、工具函数 |
| 任务边界已划定 | 本次调用只生成一个模块的代码，不跨模块 |
| 验收标准已准备 | 已准备好该模块的验收断言清单 |
| 代码库已就绪 | 目标项目已初始化，已有正确的目录结构、依赖、配置文件 |

## 三、Claude 给 DeepSeek 的 Prompt 模板

Claude 必须按以下模板构造 Prompt，禁止简化或凭经验改写：

```markdown
# 任务说明

你是鑫渠 CRM 的前端开发工程师。请严格按照下方设计文档和规范，生成【模块名】的完整前端代码。

## 一、禁止事项（必须先读）

- 禁止自行发明组件名，必须使用《鑫渠组件库清单与命名规范.md》v1.0 中定义的 Xq* 组件
- 禁止使用 PNG/JPG 图标，必须使用 SVG/Iconfont
- 禁止写死 px 尺寸作为关键布局尺寸，必须使用 CSS 变量或 Tailwind 响应式类
- 禁止使用 any 类型
- 禁止在业务代码中写死 mock 数据，必须从 props 或 API 接口获取
- 禁止省略表单校验
- 禁止省略空态、加载态、错误态
- 禁止省略移动端适配

## 二、必须读取的文档

请按顺序读取以下文档，并严格遵守：
1. /Users/mac/xinqu/AI可执行设计文档编写规范.md
2. /Users/mac/xinqu/鑫渠组件库清单与命名规范.md
3. /Users/mac/xinqu/鑫渠响应式设计规范.md
4. /Users/mac/xinqu/鑫渠字段规范模板.md
5. /Users/mac/xinqu/鑫渠验收断言编写规范.md
6. /Users/mac/xinqu/鑫渠全局设计系统规范.md
7. /Users/mac/xinqu/【模块名】功能与交互说明.md

## 三、本次任务边界

- 生成范围：只生成【模块名】的代码
- 不生成范围：不修改其它模块、不修改全局路由、不修改全局状态
- 输出目录：src/views/【模块路径】/
- 必须文件：
  - index.vue（页面入口）
  - types.ts（类型定义）
  - api.ts（接口调用）
  - mock.ts（Mock 数据，仅在接口未就绪时使用）
  - components/（子组件目录）
  - 【模块名】.test.ts（至少覆盖核心断言的测试文件）

## 四、字段与接口契约

【在此处粘贴该模块的字段规范表和接口契约表】

## 五、页面与交互要求

【在此处粘贴该模块的页面结构、布局 ASCII 图、交互规则】

## 六、验收断言

【在此处粘贴该模块的验收断言清单】

## 七、输出要求

1. 先输出文件清单和每个文件的作用
2. 再逐文件输出完整代码
3. 每个文件代码前标注相对路径
4. 最后输出自测步骤，说明如何验证本模块功能
5. 如果发现有文档缺失或矛盾，立即停止并列出问题
```

---

## 四、DeepSeek 输出规范

DeepSeek 返回的内容必须包含以下 5 个部分，缺少任何一部分 Claude 都应当拒收：

1. **文件清单**：列出所有生成文件及作用
2. **完整代码**：每个文件带相对路径
3. **类型定义**：所有业务对象、接口参数必须有 TypeScript 类型
4. **自测步骤**：至少 5 条可执行验证步骤
5. **风险说明**：列出文档中未明确、需要确认或可能出错的地方

## 五、Claude 验收 DeepSeek 输出的 Checklist

Claude 在接收 DeepSeek 输出后，必须逐项检查：

### 5.1 基础合规检查

| 检查项 | 通过标准 |
|---|---|
| 文件结构正确 | 文件清单与 Prompt 要求一致 |
| 命名规范 | 组件名使用 Xq* 前缀，页面使用 PascalCase，工具函数使用 camelCase |
| 无非法图标 | 未出现 PNG/JPG 引用 |
| 无真实 emoji | 页面文案中未出现 emoji 或彩色 Unicode 符号 |
| 无魔法数字/字符串 | 状态值、颜色、文案来自配置或常量 |
| 类型完整 | 无 any，业务对象有 interface/type |

### 5.2 设计还原检查

| 检查项 | 通过标准 |
|---|---|
| 页面结构匹配 | 与设计文档中的 ASCII 图或布局描述一致 |
| 字段完整 | 列表/表单/详情中的字段与设计文档一致 |
| 状态标签颜色 | 与设计文档中的枚举颜色一致 |
| 操作按钮 | 不同状态下显示的按钮与设计文档一致 |
| 统计卡片 | 顶部 KPI 数量、名称、颜色与设计一致 |

### 5.3 交互逻辑检查

| 检查项 | 通过标准 |
|---|---|
| 搜索筛选 | 搜索框、筛选条件、重置、实时/回车触发逻辑正确 |
| 分页 | 分页组件、页码重置、每页条数正确 |
| 视图切换 | 列表/卡片视图切换正确，默认规则正确 |
| 表单校验 | 必填项、格式校验、错误提示正确 |
| 操作反馈 | 保存/提交/删除后有 Toast/确认弹窗 |
| 空态处理 | 无数据、无权限、无搜索结果有空态 |

### 5.4 响应式检查

| 检查项 | 通过标准 |
|---|---|
| 移动端布局 | <768px 下布局正确，不出现横向滚动（表格除外） |
| 按钮不换行 | 移动端主按钮固定底部或收起为菜单 |
| 表格/卡片切换 | 移动端默认卡片视图 |
| 抽屉/弹窗 | 移动端全屏或底部弹出 |

### 5.5 接口与数据检查

| 检查项 | 通过标准 |
|---|---|
| 接口路径 | 与接口契约一致 |
| 字段命名 | 与字段规范一致 |
| Mock 数据 | 数据结构正确，便于替换为真实接口 |
| 错误处理 | 网络错误、接口报错有处理 |

## 六、代码质量标准

### 6.1 TypeScript 标准

- 所有 props、state、API 参数/返回值必须有类型
- 禁止 `any`，特殊情况需注释说明
- 枚举使用 `as const` 或 enum，禁止魔法数字
- 复杂对象使用 interface，联合类型使用 type

### 6.2 Vue 3 标准

- 使用 Composition API + `<script setup>`
- 逻辑复用使用 composables， composable 名以 `use` 开头
- Pinia store 按模块拆分，禁止在组件中直接修改其它模块的 store
- 路由跳转使用命名路由

### 6.3 样式标准

- 使用 Tailwind CSS 工具类
- 主题色、字号、间距使用 CSS 变量
- 禁止在组件中写死 `#xxxxxx` 颜色值
- 响应式使用 Tailwind 断点前缀 `sm: md: lg: xl:`

### 6.4 测试标准

- 每个模块至少一个测试文件
- 至少覆盖：渲染、搜索、表单校验、权限过滤、响应式
- 使用 Playwright 或 Vitest

## 七、禁止事项（红线）

Claude 发现 DeepSeek 输出有以下情况，必须要求重写或自行修正：

1. 私自发明不在组件库清单中的组件名
2. 使用图片图标或 emoji
3. 在业务代码中硬编码 mock 数据（mock.ts 除外）
4. 省略加载态、空态、错误态
5. 不写移动端适配
6. 不写表单校验
7. 使用 any 类型绕过类型检查
8. 接口字段命名与设计文档不一致
9. 状态值使用字符串硬编码而非枚举
10. 一个文件超过 500 行且不拆分

## 八、工作流规范

### 8.1 标准流程

```
Claude 读取设计文档和规范
    ↓
Claude 确认任务边界和验收标准
    ↓
Claude 构造 Prompt 调用 DeepSeek
    ↓
DeepSeek 返回代码
    ↓
Claude 按 Checklist 验收
    ↓
未通过 → 返回修改意见给 DeepSeek 或直接修正
    ↓
通过 → 写入代码库
    ↓
Claude 运行测试/截图对比
    ↓
测试通过 → 提交 commit
```

### 8.2 失败回退规则

- 第一次未通过：Claude 给出明确修改意见，要求 DeepSeek 重写指定文件
- 第二次未通过：Claude 停止调用 DeepSeek，分析是任务拆解不够还是文档歧义
- 第三次未通过：必须人工介入，Claude 整理问题清单交给人类工程师

### 8.3 Commit 规范

每次 DeepSeek 生成的代码通过验收后，Claude 必须按以下格式提交：

```
feat(module): {模块名} {简短描述}

- 生成 {文件数} 个文件
- 覆盖 {功能点}
- 通过 {测试数} 条验收断言
- 对应设计文档：{文档名} v{x.x}
```

## 九、性能与安全基线

### 9.1 性能

- 首屏渲染时间 <= 1.5 秒
- 列表接口响应时间 <= 800 毫秒
- 单个 Vue 文件代码量 <= 500 行，超出必须拆分
- 图片/图标必须 SVG，禁止大体积资源

### 9.2 安全

- 不在前端暴露敏感字段（如密码、密钥）
- 所有权限判断以服务端为准，前端只做展示控制
- 输入框必须防 XSS，表单提交前做转义
- 文件上传限制类型和大小

## 十、异常处理

### 10.1 文档歧义

如果 DeepSeek 在开发过程中发现设计文档有歧义，Claude 不能替它猜测，必须：
1. 记录歧义点
2. 先回查已有文档和规范
3. 如果仍无法确定，停止开发，向人类工程师确认
4. 确认后更新设计文档，再重新调用 DeepSeek

### 10.2 规范冲突

如果 DeepSeek 发现规范文档之间存在冲突，Claude 必须：
1. 按「更具体 > 更通用」原则判断
2. 记录冲突点
3. 必要时更新规范文档版本号
4. 确保后续调用使用更新后的规范
