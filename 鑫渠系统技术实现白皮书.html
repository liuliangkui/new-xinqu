02

设计原则与理念

总体设计哲学：从「看数据」到「做决策」

鑫渠的每一个页面、每一张卡片、每一个按钮，都应该让用户在最短时间内完成「认知 → 定位 → 行动」的闭环。系统不是数据的堆砌，而是决策的辅助。

认知

用户进入页面后，第一眼就能了解当前业务状态。

定位

通过导航、筛选快速找到目标数据。

行动

在目标数据上执行最合理的下一步操作。

统一五层信息架构

所有列表型页面必须遵循以下五层结构，从上到下依次排列：

1
全局指标 / 统计卡片
3-5 个 KPI，关键指标用颜色区分
2
导航 / 分类 Tab / 视图切换 / 主操作
左侧导航，右侧操作；Tab 不超过 7 个
3
搜索 / 筛选
搜索框最左，筛选条件横向排列不超过 5 个
4
明细内容（卡片网格 / 表格）
≤20 条默认卡片视图，>20 条默认列表视图
5
分页 / 加载更多
底部分页，显示页码信息和翻页按钮

双态结构

具有「数据列表 + 详情查看」的模块，统一采用双态结构。

列表态
用于扫描、筛选、定位，占据整个内容区。
详情态
用于深度查看和操作，可通过新页面、右侧抽屉、弹窗呈现。

卡片即决策单元

卡片的设计公式统一为：

卡片 = 对象标识 + 状态信息 + 下一步动作
  • • 客户卡片：要不要深入看？
  • • 线索卡片：分给谁？
  • • 意向卡片：流程走到哪？

应用划分原则

应用是面向特定角色、有独立业务闭环、能独立产生业务价值的入口。中台能力是底层复用能力，不应直接成为应用。

判断标准 适合做应用 不适合做应用
业务对象 客户、线索、意向、设备、试剂 审批记录、联系人、维修记录
角色场景 销售每天使用线索/意向/客户 360 某个配置项偶尔使用
跨业务复用 品牌库、审批中心、客户 360 仅一个模块内部使用的功能
独立价值 能回答完成什么业务目标 只是查看或配置
03

全局设计系统

设计目标

统一全系统视觉语言，确保所有页面在字体、颜色、图标、间距、圆角、响应式和主题适配上保持一致。所有规范均使用工程化可落地的方式定义，支持浅色/深色主题切换和字号缩放。

字体规范

  • • 字体栈：Inter / PingFang SC / Microsoft YaHei / Noto Sans SC
  • • 根字体 14px，大屏 15px（≥1920px），超大屏 16px（≥2560px）
  • • 字号体系使用 rem：text-2xs 到 text-4xl
  • • 所有字号支持系统字体放大而不破坏布局

图标规范

  • • 全部使用 SVG 矢量图标，禁止 emoji/PNG/JPG
  • • 图标尺寸：xs(12px) / sm(16px) / md(20px) / lg(24px) / xl(28px) / 2xl(32px)
  • • 默认继承 currentColor，选中用 --primary
  • • 图标与文字同时放大不失真

颜色体系

所有颜色使用 CSS Variables，禁止写死色值。支持浅色/深色主题切换，监听系统主题并支持手动覆盖。

系统需支持 100%/125%/150%/200% 字号放大，确保按钮不换行、布局不破坏、文本可读。

按钮与操作
  • • white-space: nowrap
  • • flex-shrink: 0
  • • 图标与文字保持同行
文本溢出
  • • 优先使用 text-overflow: ellipsis
  • • 关键信息悬停 0.8s 后自动滚动
  • • 滚动 2-3 次后停止
04

交互规范

导航规范

一级入口

侧边栏一级入口统一为：

消息 日历 工作台 通讯录 任务 应用中心 收藏

业务应用分组

业务应用统一归入应用中心，按业务域分组：

• 业务管理：线索、意向、客户 360°、设备、试剂、工单等
• 渠道协同：经销商协同
• 合规审计：合规风控
• 数据决策：目标绩效、经营驾驶舱
• 系统管理：后台设置、流程设计器、应用配置

搜索与筛选规范

全局搜索

  • • 快捷键 ⌘K / Ctrl+K 唤起
  • • 跨应用搜索客户、线索、意向、设备、工单等
  • • 支持拼音全拼、首字母、模糊查询
  • • 搜索结果按权限过滤

应用内搜索

  • • 搜索框位于列表页最左侧
  • • 实时搜索 debounce 300ms
  • • 筛选条件横向排列，不超过 5 个
  • • 搜索 + 筛选可同时生效，切换视图保留条件

弹窗使用规范

  • • 用于表单、确认、轻量操作
  • • 宽度不超过屏幕 80%
  • • 支持 ESC 关闭、点击遮罩关闭
  • • 表单弹窗必须有取消和确认按钮

抽屉使用规范

  • • 用于详情查看、分步流程
  • • 从右侧滑出，宽度 480-640px
  • • 适合线索详情、联系人详情、审批详情
  • • 复杂详情可嵌套页签

按钮层级

  • • 主按钮：页面最高频操作
  • • 次按钮：辅助操作
  • • 文本按钮：低频或危险操作
  • • 危险按钮：删除、驳回等不可逆操作

表单与审批交互

场景 推荐组件 交互要求
新建/编辑报备 弹窗 + 分步表单 必填校验、失焦查重、暂存草稿
审批/裁决 弹窗 意见必填、驳回强制详细理由、二次确认
详情查看 抽屉 / 新页面 顶部返回、关键信息固定、时间线可折叠
冲突处理 弹窗 展示冲突信息、提供查看原意向入口
跟进记录 抽屉内嵌表单 快捷标签、附件上传、自动关联对象

反馈与空态

操作反馈

  • • 保存成功：Toast 提示
  • • 提交审批：跳转待办或刷新列表
  • • 操作失败：明确错误原因
  • • 加载中：骨架屏或 Loading 动画

空态设计

  • • 无数据时显示空态插画和引导文案
  • • 提供新建入口按钮
  • • 筛选无结果时提示调整条件
  • • 权限不足时提示联系管理员
05

应用模块矩阵

模块划分说明

鑫渠 CRM 将所有功能划分为平台级入口、业务管理域、渠道协同域、合规审计域、数据决策域和系统管理域六大类。每个模块都是面向特定角色、有独立业务闭环的应用入口，底层通过业务中台和技术中台提供共享能力支撑。

5.1
平台级入口

消息中心

系统级消息聚合入口，接收审批通知、任务提醒、预警通知、系统公告、@提及等。

  • • 消息分类：待办、通知、预警、公告
  • • 已读/未读状态，支持一键已读
  • • 点击消息直达对应业务对象
  • • 支持 WebSocket 实时推送

工作台

一站式每日工作入口，聚合待办、日程、KPI、常用应用和快捷操作，减少跳转成本。

  • • 待办中心：审批待办、任务待办、预警待办、系统待办
  • • 今日日程：按时间轴展示拜访、会议、任务
  • • 我的 KPI：本月意向、成交率、拜访数等
  • • 快捷入口：最近访问、收藏应用

通讯录

企业级联系人管理，覆盖内部员工、经销商、客户决策链联系人。

  • • 组织架构树：按部门/区域/经销商层级展示
  • • 客户联系人：关联客户 360° 决策链
  • • 权限隔离：按数据范围控制可见联系人
  • • 快速拨号、发送消息、预约拜访

任务

个人与团队任务管理，支持任务分配、跟踪、提醒和完成闭环。

  • • 任务分类：拜访任务、跟进任务、审批任务、自定义任务
  • • 负责人/协同人/截止时间
  • • 任务状态：待办 / 进行中 / 已完成 / 已逾期
  • • 自动同步到日历和待办

应用中心

全部业务应用和系统应用的统一入口，按业务域分组展示。

  • • 业务管理、渠道协同、合规审计、数据决策、系统管理分组
  • • 支持应用搜索和收藏
  • • 按角色权限动态显示可用应用
  • • 常用应用置顶

收藏夹

用户自定义的快捷入口，收藏常用页面、客户、意向、报表。

  • • 支持收藏页面、业务对象、筛选视图
  • • 跨设备同步收藏数据
  • • 工作台显示最近收藏

5.2
业务管理域

线索管理

渠道秩序域前置入口。负责收集、查重、分配、跟进销售线索，为意向报备提供经过初筛的商机来源。线索是登记层（低门槛、不审批、公海池），意向是授权层（高门槛、需审批、保护期）。

核心流程：录入 → 查重 → 分配 → 跟进 → 转意向
页面布局：4 个 KPI + Tab 分组 + 列表/卡片视图
关键规则：7 天未跟进自动回收公海池

意向管理

IVD 行业销售过程管控域核心模块。管理从意向提交到项目结束的全生命周期，防止撞单、规范审批、区分业务模式。

业务类型：招标项目、非招标常规、TP/捐赠
核心状态：草稿、审批中、生效中、冲突无效、驳回、已结束
关键规则：唯一生效原则、冲突审批规则、招标送货规则、TP/未装机规则、保护期规则

审批中心

跨业务的通用审批入口，面向审批人角色统一处理待办。虽然审批是技术中台能力，但面向审批人的工作入口具有独立的业务价值，因此作为应用存在。

覆盖业务：意向报备、冲突裁决、设备投放、合规活动、费用报销
待办分类：待我审批、我已审批、抄送我的、我发起的
操作能力：通过、驳回、转交、加签、批量审批

客户 360°

客户资产中心和数据枢纽，聚合 HCO/科室/决策链/设备/试剂/时间线数据，解决客户信息分散、健康度不可见、交叉销售机会难发现的问题。

详情页 6 个页签：概览、科室、决策链、设备地图、试剂账本、时间线
健康度评分：设备活跃 25% + 试剂消耗 25% + 关系维护 20% + 商业贡献 20% + 服务体验 10%

设备管理

设备是 IVD 的"阵地"，确保每台设备从售前到报废全程可控、可追踪、可运营。覆盖招标跟踪、装机管理、设备台账、运行监控、维保工单、保修到期提醒。

使用角色：销售代表、FAE、售后服务工程师、售后主管
核心场景：故障智能派单、维保计划、保修预警、利用率监控
价值：故障响应时间缩短 50%，设备利用率提升 15-25%

试剂运营

把试剂从"被动销售品"变成"可预测、可运营、可增值的资产"。覆盖试剂绑定、消耗记录、库存监控、AI 补货预测、复购预警、流失预警。

使用角色：销售代表、经销商、供应链经理、财务
核心场景：断货预警、客户流失预警、多级库存监控
价值：试剂复购率提升 15-30%，断货率降低 60%

售后工单

设备故障和服务请求的处理中心，支持报修、派单、处理、回访、满意度评价全流程。与设备管理、日历、客户 360° 深度联动。

工单类型：故障维修、保养维护、培训支持、配件更换
派单规则：区域优先、技能匹配、负荷均衡、客户偏好
SLA 监控：响应时效、解决时效、满意度评分

工单看板

售后工单的流程可视化视图，按工单状态（待处理 / 处理中 / 待回访 / 已完成）展示为看板列，支持拖拽变更状态、快速分配、SLA 预警。

视图形态：看板视图 / 列表视图 / 日历视图
核心能力：拖拽流转、快速分配、状态筛选
适用角色：售后主管、工程师、调度员

品牌库管理

产品/品牌主数据管理中心，跨业务复用。管理品牌信息、产品型号、规格参数、适用设备、资质文件、Logo 等。

数据范围：品牌、产品线、型号、规格、资质、Logo
应用场景：意向报备选品、设备台账、试剂绑定
管理权限：产品经理维护，业务端只读引用

5.3
渠道协同域

经销商协同

把经销商从"被管理的渠道"变成"协同服务的伙伴"，实现厂家与经销商的信息共享和业务协同。覆盖经销商档案、经销商门户、库存共享、返利引擎、任务协同、业绩看板。

使用角色：渠道经理、经销商老板/业务、销售代表、财务
核心场景：窜货冲突预警、返利自动核算、库存共享
价值：渠道冲突减少 50%，返利核算效率提升 80%

5.4
合规审计域

合规风控

在强监管环境下，确保销售、推广、服务全过程合规可追溯，降低企业法律风险。覆盖代表备案、拜访合规、学术活动管理、样品/赠品管理、飞检抽查、敏感词审计。

使用角色：合规经理、销售代表、地区经理、法务/内审
核心场景：反商业贿赂审计、学术活动合规、设备投放合规
价值：合规审计准备时间缩短 70%，违规事件降低 70%

5.5
数据决策域

目标绩效

目标拆解与达成跟踪，支持年度/季度/月度目标层层分解到区域、团队、个人。

  • • 指标类型：销售额、装机量、试剂消耗、客户覆盖、拜访数
  • • 目标拆解：公司 → 大区 → 团队 → 个人
  • • 达成率实时计算，支持同比环比
  • • 未达标预警和下钻分析

经营驾驶舱

高管全局决策入口，汇总设备装机量、试剂销售额、客户健康度、经销商绩效等核心指标。

  • • 多维度下钻：按区域 / 产品线 / 时间

双中台命名说明

鑫渠当前阶段采用业务中台 + 数据中台的双中台架构。工作流、权限、搜索、消息等通用技术能力属于技术基础设施层（也可称为技术平台），它们支撑业务中台和数据中台运行，但本身不属于数据中台。

架构演进路线

演进必要性

双中台能解决当前阶段的业务能力复用和数据汇聚问题，但随着 AI 能力深化、实时性要求提升、组织规模扩大，需要向智能驱动、事件驱动、可组合架构演进。

第一阶段 0-12 个月

双中台 + DDD

夯实基础，支撑 1000 人并发，沉淀核心业务能力。

业务中台：客户、线索、意向、设备、试剂、工单、审批等核心领域能力
数据中台：统一数据采集、治理、报表、指标体系
DDD 建模：明确聚合根、限界上下文、领域事件
后台配置化：字段、视图、流程、标签、权限可配置
第二阶段 12-24 个月

AI 中台 + 事件驱动

引入智能化能力和实时业务流程联动。

AI 中台：线索评分、客户流失预警、试剂消耗预测、智能助手
事件驱动：意向成交→设备装机→试剂跟踪自动串联
实时计算：库存预警、待办提醒、经营指标实时刷新
数据中台升级：实时数仓、指标平台
第三阶段 24-36 个月

可组合架构 + 数据网格/湖仓一体

让系统具备高度灵活性，支持多组织、多产品线、多业务模式。

PBC 化：每个领域能力封装为可复用的打包业务能力
低代码平台：业务人员可配置页面、流程、报表
数据网格：各领域团队负责自己的数据产品
AI 原生交互：自然语言查询经营数据

单体起步，按需拆分
业务边界稳定、团队规模扩大后再拆分微服务
中台能力先于组织拆分
先沉淀可复用能力，再考虑独立团队

AI 可执行开发指南

本章节定义鑫渠 CRM 面向 AI 编程 agent 的开发执行标准。核心目标是：任何 AI 编程 agent 在阅读对应模块设计文档后，能够直接输出符合设计、交互、视觉与数据模型要求的前后端代码，减少理解偏差与返工。

12.1
为什么需要 AI 可执行文档

传统设计文档面向人类阅读，常存在描述模糊、缺省字段、组件不统一等问题。AI 编程 agent 无法像人类一样依赖经验补全信息，因此设计文档必须达到「可执行」精度。

最高使命

让任何 AI 编程 agent 拿到文档后能 100% 按设计开发，无需二次询问、无需依赖个人经验、无需猜测业务规则。

  • • 无歧义：同一句话只能有一种理解方式。
  • • 可量化：所有尺寸、颜色、间距、状态、权限都有明确数值或枚举值。
  • • 可映射：每一处 UI 都能对应到具体组件名、字段名、接口名。
  • • 可验证：每个功能都有至少一条可自动化验证的断言。
  • • 双端一致：PC 端与移动端必须分别描述，不能混为一谈。

12.2
AI 开发三层 agent 协作架构

为提高 AI 开发的可控性与质量，采用三层 agent 分工协作模式：架构层把控全局、实现层输出代码、验收层独立验证。

架构层
Claude / 同等强推理模型

负责理解业务、拆解模块、制定技术方案、定义接口与数据模型、识别边界条件。

实现层
DeepSeek-V4 1M / Claude 4 / 同等长上下文编码模型

在架构层方案约束下，按设计文档输出页面、组件、接口、状态机、测试代码。

验收层
专用测试 agent

对照验收断言清单逐项验证，输出测试报告，标记不通过项并给出修复建议。

12.3
文档结构标准

每份应用模块文档必须按以下 12 个必填章节顺序编写，缺失任一章节视为不合格。详见《AI可执行设计文档编写规范.md》。

1. 文档基础信息
2. 机器指令块
3. 模块定位与目标
4. 使用角色与权限
5. 核心业务流程
6. 页面清单与路由
7. 页面结构与布局
8. 核心字段规范
9. 交互设计要点
10. 接口契约（前端视角）
11. 验收断言清单
12. 关联与扩展

12.4
字段规范

每个业务字段必须给出完整定义，禁止只有中文名称的模糊写法。详见《鑫渠字段规范模板.md》。

属性 说明
字段编码英文/拼音驼峰或下划线编码，全局唯一
数据类型String / Number / Integer / Boolean / Date / DateTime / Enum / Array / Object / Money
长度/精度字符串长度、数字精度、日期格式
是否必填是 / 否 / 条件必填
读写权限角色可见/可编辑规则，是否脱敏
渲染方式列表/详情/表单中如何展示，映射到具体组件

12.5
组件映射

所有 UI 必须映射到《鑫渠组件库清单与命名规范.md》中注册的 Xq* 组件，禁止自行发明组件名。

布局：XqPageLayout / XqTwoColumnLayout / XqDrawer
数据展示：XqKpiCard / XqDataTable / XqCardGrid / XqStatusBadge
表单：XqSearchBar / XqFilterBar / XqFormDrawer
导航：XqNavTabs / XqViewSwitch / XqBackButton
反馈：XqToast / XqConfirmDialog / XqEmptyState
业务：XqIntentionCard / XqLeadCard / XqCustomerCard / XqTimeline

12.6
接口契约

每个模块必须给出前端视角的接口契约，确保实现层 agent 与后端对接有据可依。

  • • 接口名：统一英文驼峰命名，如 getIntentionList、createIntention。
  • • 请求方式：GET / POST / PUT / DELETE，按 REST 语义选择。
  • • 请求路径：/api/v1/模块/动作，版本与模块清晰。
  • • 入参：字段编码、类型、必填、默认值、说明。
  • • 出参：字段编码、类型、说明，列表需包含分页信息。

12.7
验收断言

每个核心功能至少编写 3 条可自动化验证的断言，覆盖正常流、异常流与边界条件。详见《鑫渠验收断言编写规范.md》。

功能断言
验证业务功能是否按预期工作
表单校验断言
验证必填、格式、长度等校验规则
权限断言
验证不同角色可见范围与操作权限
搜索筛选断言
验证关键词、拼音首字母、筛选条件
响应式断言
验证 PC 端与移动端布局一致性
性能断言
验证首屏渲染、接口响应、翻页速度

12.8
响应式双端设计

每个页面必须分别描述 PC 端和移动端布局，禁止只写 PC 端或一句话「移动端适配」。详见《鑫渠响应式设计规范.md》。

PC 端（>=1024px）
  • • 多列布局，统计卡片横向排列
  • • 表格完整列展示，支持固定列
  • • 筛选条件横向平铺或抽屉
  • • 详情使用右侧抽屉
移动端（<768px）
  • • 单列卡片列表，底部固定操作
  • • 表格切换为卡片或横向滚动
  • • 筛选收起为底部抽屉
  • • 详情为全屏页面，顶部返回

12.9
开发执行建议

基于 AI 开发实践，总结以下执行建议，降低返工率并提升代码质量。

分而治之

将复杂模块拆分为独立页面、组件、接口、状态机，分别生成 prompt 与验收断言，避免单次 prompt 过长导致信息丢失。

先接口后页面

先由架构层 agent 定义并评审接口契约，再由实现层 agent 基于契约开发页面，减少前后端字段不一致。

先骨架后细节

先实现页面骨架、路由、状态管理，再填充字段校验、权限判断、异常处理等细节。

视觉回归

对关键页面执行截图对比，确保实现与原型在布局、间距、颜色、字体上保持一致。

代码审查 agent

引入独立审查 agent 检查命名规范、组件复用、字段一致性、接口契约符合度、是否引入真实 emoji 或 PNG/JPG 图标。

12.10
Claude-DeepSeek 协同开发规则

当使用 Claude 作为主控 agent、DeepSeek 作为实现 agent 时，必须遵守《Claude-DeepSeek协同开发规则.md》中的约束。

角色分工

Claude 负责任务拆解、准备上下文、验收结果；DeepSeek 负责在精确上下文内生成代码。

调用前提

设计文档已通过验收、接口契约已确认、任务边界已划定、验收标准已准备。

Prompt 模板

Claude 必须按规则中的模板构造 Prompt，包含禁止事项、必读文档、任务边界、字段接口、验收断言。

验收 checklist

Claude 必须对 DeepSeek 输出做基础合规、设计还原、交互逻辑、响应式、接口数据五层验收。

详见《Claude-DeepSeek协同开发规则.md》。
